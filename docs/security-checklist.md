# قائمة تدابير الأمان والحماية المؤسسية
## Enterprise Security Checklist, Anti-Spoofing Protocols and RBAC Controls

---

## 1. أمان الهوية والمصادقة (Authentication and Password Security)

- [x] **تشفير كلمات المرور عبر خوارزمية Bcrypt:**
  - يتم استخدام الدالة المعيارية `password_hash($password, PASSWORD_BCRYPT, ['cost' => 12])` لتوليد تجزئة كلمة المرور بصورة غير قابلة للعكس مع ملح عشوائي تلقائي (Salt).
  - يتم التحقق الآمن عبر `password_verify($password, $user['password'])` لحماية النظام من هجمات توقيت التنفيذ (Timing Attacks).
- [x] **حماية الرمز المميز (JWT Token Architecture):**
  - استخدام خوارزمية التوقيع الرقمي `HMAC-SHA256` (HS256) مع مفتاح سري عالي الإنتروبيا (`APP_KEY` لا يقل عن 64 محرفاً عشوائياً).
  - ترويسة الطلب المعتمدة حصرياً: `Authorization: Bearer <TOKEN>`.
  - حمولة الـ JWT تحتوي فقط على المعرفات غير الحساسة: `user_id`, `email`, `role`, مع تاريخ انتهاء الصلاحية (`exp`).
  - التحقق الإجباري في كل استدعاء API من صلاحية التوقيع وتاريخ الانتهاء قبل توجيه الطلب لأي Controller.

---

## 2. ضوابط الصلاحيات الصارمة (Strict Role-Based Access Control - RBAC)

- [x] **مبدأ الامتيازات الأقل (Principle of Least Privilege):**
  - تصنيف المستخدمين إلى مستويين صارمين: مدير النظام والمالك (`owner`)، والموظف (`employee`).
- [x] **حظر الموظفين التام من العمليات المالية:**
  - الموظف غير مصرح له مطلقاً بطلب صرف ذاتي للبونص (`/api/points/claim-bonus` محظور على مستوى الـ Backend برمز `403 Forbidden`).
  - تحديد وتعديل مبالغ الخصومات وتوزيع المكافآت محصور حصرياً بالمدير التنفيذي عبر الـ Endpoints التالية:
    - `POST /api/owner/apply-deduction`
    - `POST /api/owner/grant-bonus`
    - `POST /api/owner/bonus-settings`
- [x] **عزل سياق المستخدم (User Context Isolation):**
  - في جميع مسارات الموظف (مثل تقديم الإجازات، تسجيل التظلمات، تحديث InstaPay، واستعراض الحضور الشهري)، يتم استخراج `user_id` من توكن الـ JWT المفكك فقط، ولا يُقبل أي `user_id` ممرر من الـ Request Body، مما يمنع انتحال الهويات (IDOR Attacks).

---

## 3. حماية البصمة الجغرافية ومكافحة التلاعب (GPS Anti-Spoofing Protocols)

- [x] **التحقق الرياضي من الإحداثيات عبر معادلة Haversine:**
  - يتم حساب المسافة الفاصلة بين إحداثيات جهاز الموظف والفرع المعتمد برمجياً على السيرفر عبر معادلة Haversine المعيارية:
    $$d = 2R \cdot \arcsin\left(\sqrt{\sin^2\left(\frac{\Delta\phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta\lambda}{2}\right)}\right)$$
    حيث أن $R = 6,371,000$ متر (متوسط نصف قطر الكرة الأرضية).
- [x] **فلترة دقة إشارة الـ GPS (Accuracy Threshold Filter):**
  - في بيئة الإنتاج (`APP_ENV=production`)، يتم فحص الحقل `accuracy` المُستلم من حساس الـ GPS بالجهاز.
  - أي قراءة تزيد عن الحد الأقصى المسموح به (`MAX_ALLOWED_ACCURACY_METERS = 50.0m`) تُرفض تلقائياً برمز خطأ `400 Bad Request` وتنبيه مضاد للتلاعب (Anti-Spoofing Defense).
- [x] **إلغاء وضع المحاكاة في بيئة الإنتاج (Simulation Gate):**
  - يتم ضبط المتغير `ALLOW_SIMULATION=false` في ملف `.env` الإنتاجي.
  - يتجاهل السيرفر أي بارامترات للمحاكاة مثل `simulated_time` أو `allow_recheckin` ويجبر الاعتماد على التوقيت والإحداثيات الحقيقية فقط.
- [x] **التحقق من الفروع المعتمدة (Branch Geofencing Match):**
  - لا يمكن للموظف إرسال إحداثيات فرع وهمية؛ يتم التحقق من وجود الفرع في جدول `branches` مع شرط `is_active = 1`.

## 4. إجبارية توقيت الخادم (Server Time Authority)

- [x] **تجاهل التوقيت المحلي للأجهزة (Client Clock Independence):**
  - لا يعتمد النظام إطلاقاً على توقيت هاتف أو متصفح العميل لتفادي التلاعب بتقديم أو تأخير ساعة الجهاز.
  - يتم احتساب توقيت البصمة والنافذة الزمنية اعتماداً حصرياً على `NOW()` وساعة السيرفر المزامنة عبر بروتوكول NTP.
- [x] **قواعد النوافذ الزمنية الصارمة:**
  - البصمة قبل الساعة 07:00 ص: البوابة مغلقة تلقائياً.
  - الحضور المبكر: من 07:00 ص حتى 08:59 ص (+1 خضراء و +1 كريديت تعويضي).
  - فترة السماح الرسمية: من 09:00 ص حتى 09:15 ص (+1 خضراء).
  - فترة التأخير: من 09:16 ص حتى 11:59 ص (استهلاك درع الحماية أو +1 حمراء وخصم تأخير).
  - إغلاق البوابة اليومي (Cutoff Gate): في تمام الساعة 12:00 ظهراً يُقفل الحضور وتُقيد نقطة سوداء وخصم يوم كامل.

## 5. سلامة المعاملات المالية وقاعدة البيانات (Financial & Database Integrity)

- [x] **المعاملات المتكاملة (ACID PDO Transactions):**
  - أي عملية تؤثر على رصيد مالي ونقاط متعددة (مثل الخصم أو المكافأة أو تفعيل درع الحماية) يتم تغليفها داخل:
    ```php
    $pdo->beginTransaction();
    // تنفيذ استعلامات الخصم وإضافة قيد الليدجر
    $pdo->commit();
    ```
    مع إرجاع التغييرات فوراً `rollBack()` في حال حدوث أي استثناء أو خطأ.
- [x] **منع الأرصدة السالبة (Underflow Prevention):**
  - جميع استعلامات الخصم المالي تستخدم الدالة الحسابية في SQL:
    ```sql
    UPDATE users SET financial_balance = GREATEST(0, financial_balance - ?) WHERE id = ?
    ```
    لضمان عدم هبوط رصيد الموظف دون الصفر مهما بلغت الخصومات.
- [x] **الحماية الشاملة من حقن الاستعلامات (SQL Injection Prevention):**
  - جميع التعاملات مع قاعدة بيانات MySQL تتم بنسبة 100% عبر الاستعلامات المجهزة المسبقة (Parameterized Prepared Statements). لا يتم دمج أي متغير نصي مباشر داخل جمل الاستعلام.

## 6. الرقابة والامتثال وسجل التدقيق (Audit Logging)

- [x] **تسجيل القرارات الإدارية الحساسة في جدول `audit_logs`:**
  - تطبيق خصم مالي يدوي مع ذكر السبب والمبلغ.
  - منح مكافأة إضافية أو بونص يدوي من المدير.
  - تعديل سياسات المنظومة (مبالغ البونص والخصومات).
  - مراجعة طلبات الإجازات وقبول أو رفض التظلمات.
  - تصدير كشوف الرواتب والتحويلات البنكية لملفات Excel / PDF.
- [x] **حماية ملفات وبيانات الاتصال:**
  - ملفات `.env` محمية من العرض المباشر عبر إعدادات خادم الويب (Nginx / Apache).
  - حظر الوصول لمسارات الملفات المؤقتة وأدوات الاختبار خارج بيئة التطوير.
